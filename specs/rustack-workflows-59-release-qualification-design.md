## 1. Consumer completion

O01's named Native snapshot consumer must hold all five outstanding forms at the same graceful cutoff: Wait, callback, Retry backoff, an inline Map with a waiting iteration, and an owned nested `.sync:2` child. Poll actual history until the corresponding state/Task failure/Map iteration/child-start event is present, rather than sleeping and assuming entry. On restart each outstanding execution is ABORTED/Rustack.Shutdown, no successor marker runs, no callback token remains usable, and no prior computation is replayed. Snapshot failure after unconfirmed physical cleanup must preserve the preceding generation; the Docker transport-loss consumer checks this actual binary path.

O03 must consume actual named archives with a moved operator alias A→B, retaining source A/B by immutable IDs. A cold restore must select saved A; a syntactically valid archive referring to an absent immutable ID must reject even when source B is locally available. Separate valid-checksummed owner and engine affiliation mismatches must reject before publishing readiness. Each rejected startup preserves current/previous snapshot fingerprints and both source IDs. Fixture faults mutate a private copy of metadata/affiliation only; never remove an operator image or retag canonical fixtures.

O04 runs two actual live binaries with distinct private data roots on one explicit engine. Establish a warm survivor invocation, SIGKILL and join the other binary, restart the crashed owner, then assert the survivor's exact container ID and warm counter survive recovery and continue to advance. Check concurrent signed readiness during recovery; stop/join both and require scoped zero owned resources. Failure keeps evidence rather than deleting uncertain resources.

O05 adds a composite consumer with a large nested ASL payload and an oversized Runtime response. While work is active, signed control calls/readiness and Stop must complete within existing budgets. Assert typed quota/protocol outcomes and physical environment retirement, then admit and complete a fresh request. Existing infinite-loop and 100 log-flood-timeout consumers remain mandatory.

Add every new ignored resource name to the canonical eight-suite Docker manifest; consumers derive cardinality from that exact manifest and reject missing/extra compiled names. No hard-coded historic resource count may narrow the new cohort.

## 3. Complete release evidence

`verify-workflows` is the final, non-skipping evidence assembler. An input bundle contains source-bound raw lane receipts and exact candidate archive seals. Required lanes are Rust gates, Native, Linux arm64 functional, rootless arm64 functional, Docker Desktop, dedicated arm64 pure/image performance and load, plus release-image qualification. No `pending`, focused-only, skipped, waived non-x86 lane, missing required resource or nonzero command may pass. D100 is the sole fixed waiver; never convert Desktop/reference unavailability into success.

Each lane envelope carries schemaVersion=1, lane, commit, sourceSealSha256, status=passed, allChildGroupsJoined=true, exact resource-name inventory and SHA-256-bound raw receipts. The bundle also records candidateRunId (a numeric Actions run ID, or local for non-publication work). Rust receipts include the actual gate report, entry, every exact argv intent and log; default and feature doctests are required in addition to all-target tests. Reference envelopes bind the original pure/image producer reports; revalidate all raw samples, ranks, live brackets, cleanup and unchanged summary metrics. Physical dedication is an explicit operator attestation, never inferred from virtual CPU count. Platform envelopes bind an actual explicit-daemon platform receipt; rootless/Desktop attribution comes from engine metadata and zero-resource observations. Release logs must contain both typed consumer records with exact source image ID, container/engine identity and successful physical cleanup; an image ID claimed only in the envelope is insufficient. Only repository-known lane names and resource inventories are accepted. Candidate seals include architecture, archive byte count/SHA-256, exact immutable daemon-addressable Docker image ID and a separately verified configDigest (Docker containerd stores may address a manifest/index rather than the config), commit and source seal. All receipts and archives are bounded regular files under the bundle; reject traversal, symlinks, duplicates and unrelated commits/source cohorts. The assembled report records hashes of every input and both candidate seals; it is evidence, not a signature or permission to publish.

## 4. Build, qualify, promote

                               ▼ immutable run artifacts

│ verify-workflows → complete release report + candidate seals       │
└──────────────────────────────┬────────────────────────────────────┘
                               ▼ explicit promotion workflow inputs
┌─ promote-docker: only job holding packages:write ──────────────────┐

Candidate creation never logs in or pushes. Promotion accepts candidate and qualification run IDs, verifies both successful same-repository workflow runs and same head commit, downloads immutable artifacts, and executes the assembler again. No source rebuild occurs after qualification. Only after all checks succeed may registry credentials enter the distinct promotion job. Publication is not run locally. Invalid/missing evidence must prevent login and push, including manual dispatch. Actions are pinned by full commit SHA to current official releases.

## 6. Artifact schema and operator handoff

Use the canonical source seal from the retained controllers. Stage a private0700 bundle with bundle.json, two candidate-<architecture>.json seals (each retaining distinct imageId/configDigest), their release-<architecture>.tar archives and seven lane JSON envelopes. bundle.json keys are schemaVersion, commit, sourceSealSha256, candidateRunId, candidates (two relative seal paths) and lanes (the seven fixed lane names mapped to relative envelope paths). Each envelope has exactly schemaVersion/lane/commit/sourceSealSha256/status/allChildGroupsJoined/tests/receipts/qualification. Each receipt has path/sha256/code=0/groupJoined=true. Paths are relative, component-validated, non-symlink regular files. Each lane permits at most512 bound receipts. Lane logs have a256MiB aggregate bound and16MiB/file; JSON is bounded to1MiB, depth16,32,768 members and16KiB/string. Config/archive identities are checked independently of Docker's current image cache, with fixed-block TAR preflight before any eager parser. The arm64 candidate additionally passes the existing exact filesystem/ELF verifier.

Qualification fields are lane-specific: Rust uses gates/report/entry/intents; reference uses referenceQualification/os/architecture/physicalCpus/exclusive, pureP95Micros/warmOverheadP95Micros/coldEndToEndP95Micros/loadCycles, and pureReport/imageReport; platform lanes use os/architecture/engineId/rootless/desktop/zeroOwnedRemnants/platformReport/executionReport/executionEntry/caseReceipts; Native uses nativeChildrenJoined plus the same gates/report/entry/intents producer fields as Rust; release uses imageId/zeroOwnedRemnants, corroborated by typed WORKFLOWS_RELEASE_RESOURCE records. Raw reports, entry/intents and platform reports must themselves appear in the bound receipts list. Platform execution must come from the exact controller report/entry on that same endpoint/engine/source seal, with every canonical case mapped to its original intent/result/stdout/stderr and revalidated argv, exit code, hashes and one-resource summary. A rootful test log plus a fresh rootless postcondition receipt must fail. Linux/Desktop use test-workflows-docker-functional with an explicit topology JSON; rootless retains its attested controller. Both share one strict compiled-inventory/case sequence. Performance limits remain pure100ms, warm adapter overhead50ms and cold end-to-end5s, with100 load cycles; this delivery work does not tighten or relax them.

`workflows-platform-receipt` records the final explicit engine metadata and empty-resource observations. `workflows-release-evidence` validates and copies only referenced inputs to a fresh artifact directory (at most2,048 files/6GiB), revalidating the copy. The workflows-evidence workflow requires a deliberately configured self-hosted rustack-qualification runner and WORKFLOWS_EVIDENCE_ROOT repository variable pointing to the staged bundle. Missing infrastructure/evidence is a concrete release dependency, never an automatic success. Its immutable artifact feeds qualify-workflows, which independently checks the candidate/evidence run provenance and reruns verify-workflows; promote-docker accepts only that successful same-commit qualification run. Only promotion holds packages:write. The actual push digest is captured, its immutable remote manifest/config binding rechecked, and only those digests form public version manifests.

Negative controls cover A-consumer/B-candidate substitution, missing modes, modified/duplicate/failed receipts, fake Rust logs without producers, contradictory reference summaries, lane aggregate limits, traversal/symlinks, duplicate/deep/nonfinite JSON, oversized PAX/GNU extensions, archive config identity, transient GH token scoping and remote tag/config races. These controls are code-complete before execution begins; writing them is not evidence that they passed.

The Linux/Desktop topology JSON has exactly socket, otherSocket (a distinct actual installation), daemonSocket (container-visible daemon path), socketGid, network, gateway, fixtures, sdk, target and buildReceipt. Paths are explicit absolute values; the gateway is a private IPv4 address and the supplied network must be an existing bridge. The fresh production-image build receipt must match the current source seal, daemon, runtime/custom-RIC A/B/server/release IDs and bounded build-log hash. This prevents a newly sealed test controller from silently consuming stale production binaries. No controller provisions or changes a Docker context, VM or daemon.
